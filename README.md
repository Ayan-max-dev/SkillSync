# SkillSync
#### Video Demo: https://youtu.be/VJX7s4oqMZ8>

#### Description:
Web app link: https://ayanashraf17.pythonanywhere.com/

SkillSync is a web application built with Flask that turns informal, word-of-mouth skill-sharing inside a school into something organised and searchable. The idea came from a simple observation: in any school, students and teachers already have a huge range of skills and hobbies between them — coding, chess, photography, a language, public speaking — but there's no structured way for someone who wants to learn one of those things to find the person who could teach it. Those connections usually only happen by chance, through a friend or a classmate who happens to know someone. SkillSync exists to remove that luck factor. It gives every student and teacher a place to offer a skill they can teach, post a request for something they want to learn, browse and search what's on offer, and turn a match into an actual scheduled session — either live or as a recorded lesson — with attendance, feedback and a reputation record attached to it.

The guiding principle behind the design is that everyone can be both a learner and a teacher at the same time, so the platform treats "offering" and "requesting" as two equally first-class actions rather than building around a fixed teacher/student hierarchy. A second guiding principle, given that this is meant for real deployment in a school and not just a demo, was that safety and moderation couldn't be an afterthought: every piece of user-generated content (offers, requests, comments, session recordings) can be reported, and every report is reviewed by a human admin before anything is hidden — nothing is ever silently auto-removed, and nothing a moderator hides is ever permanently deleted, only flagged so it can be restored if the decision was wrong.

**How the project is organised.** The application follows a standard Flask application-factory pattern with blueprints, so that each area of functionality lives in its own package instead of one giant file. `extensions.py` holds the shared Flask extension instances (SQLAlchemy, Flask-Login, Flask-WTF's CSRF protection, Flask-Limiter, Flask-Migrate) so they can be initialised once and imported anywhere without causing circular imports — an early version of the project ran into exactly that problem before this was pulled out into its own module. `models.py` defines the database schema: users, skill offers, learning requests, sessions, comments, feedback, and reports, along with the relationships between them. From there, each blueprint package owns one area of the app: `auth` handles login, logout and account creation; `profiles` handles viewing and editing a user's public profile — bio, grade, skills taught and learned, and a reputation summary built from average rating, sessions taught, and earned badges; `offers` and `learning_requests` handle creating, browsing and searching skills people are teaching or looking for; `sessions` handles scheduling, enrollment, attendance and recordings; `reports` lets any user flag an offer, request, comment or recording that needs attention; `notifications` handles the updates users get for things like enrollment confirmations, cancellations and feedback reminders; `admin`, gated behind an `is_admin` check, gives moderators the reports queue with status filters and one-click hide/restore actions, separate from the `reports` blueprint that files them; and `main` holds the dashboard and general routes. Templates live under `templates/`, organised to mirror the blueprints, all extending a shared `base.html` that defines the site's navigation and a custom visual theme (an ink-navy and chalk-amber colour palette with Source Serif and Work Sans typography) so the whole app feels consistent rather than like a stack of default Bootstrap pages. Static assets live under `static/`. The SQLite database file sits in `instance/`, kept out of version control the way Flask expects. A `seed.py` script populates the database with realistic test accounts and sample data, which turned out to be far faster for re-testing after a schema change than manually re-creating data by hand every time. Database schema changes are managed through the `migrations/` folder via Flask-Migrate rather than dropping and rebuilding the database, so existing data survives every update. A `tests/` directory holds an automated test suite covering authentication, authorization and data-integrity behaviour, run against an in-memory database created through the app factory's test configuration.

**Design choices I debated.** The biggest one was how "moderation" should behave: my first instinct was to just delete anything an admin hid, but I decided against it, because a wrongly-hidden offer or comment should be recoverable, and a full historical record matters more than a smaller database. Everything hidden by moderation is flagged, not destroyed. A related decision was around what counts as a "session taught" for someone's public reputation — I initially tracked both "completed" and "taught" as separate stats, but they overlapped in a way that was confusing to display, so I dropped "completed" and kept a single, clearly-defined rule: a session counts as taught only if it ended, wasn't cancelled, and every enrolled student had attendance marked. I also went back and forth on performance: some profile statistics were originally computed as Python model properties, which caused N+1 query problems as the number of users grew. I replaced those with SQL aggregate queries and `selectinload()` for batch-loading related data instead. Lastly, I prioritised security fixes (proper password hashing, CSRF protection on every form, and rate limiting on login/signup) ahead of visual polish, on the basis that a good-looking but insecure app is worse than a plain but safe one for something real students and teachers will actually use.

The app is currently deployed and live on PythonAnywhere, and is being prepared for a pilot with real students and teachers at school.
